# candor-intake-store — SPEC-NOTES

Component C-08 (Intake Store). Sources: 09-DATABASE.md §5.1, §8, §10, §11; 07-BACKEND.md §5.3, §5.4, §6.3, §12; 08-API.md RL-01..RL-12, SA-19/SA-20, §3.8; ADR-009/010/033/034/038/039/046(1)/047(2,3,9)/052; research/R7 §E; process/audits/AUDIT-RM2-intake-store.md.

## Scope

**Delivered:**
- the `IntakeStore` trait (owner of the intake persistence interface);
- `PgIntakeStore` (sqlx 0.9, PostgreSQL 16);
- `MemoryStore`;
- the signed deletion list;
- the fetch-all dead-drop pages;
- the KD snapshot high-water mark;
- monthly counters (flushed at import slots) and backup/restore content;
- the separate maintenance handle (`PgIntakeMaintenance`);
- the schema lint;
- the test cluster script.

**Not in this assignment (left for the C-08 daemon / follow-ups):**
- Tier V `upload` / `upload_chunk` tables;
- `config_bundle` (RL-07);
- `job_local`;
- tmpfs staging;
- blob file I/O (`candor-safefs`);
- the SEQPACKET IPC and the TLS 1.3 relay endpoint;
- `ACCOUNT_ROTATE` beyond the account-row update (`update_account`; reply-stanza replacement belongs to the daemon);
- typed audit events (`candor-log`);
- encryption of the RL-10 snapshot to the Backup Key;
- 24 §TEL suppression of RL-09 counters.

None of these weaken anything here. Tables that do not exist cannot leak.

## Implementation decisions

1. **`lookup_tag` = `locator_hash`.** 04 §11.4 calls it `lookup_tag`; 09 §5.1 calls the column `locator_hash`. The column keeps the 09 name and the Rust type is `LookupTag`.
2. **`envelope.epoch_index integer` added** (not in 09 §5.1). RL-02 must send `epoch_index`. 09 says `received_date` is "used only to derive the sealing epoch", but no derivation rule (epoch origin) is specified anywhere, and Tier V clients may seal for a ±1-day-skewed epoch. So the store keeps the epoch the sealer reports. It is weekly granularity, coarser than `received_date`, so it adds no information. *Spec feedback:* add the column to 09 §5.1, or specify the derivation.
3. **`intake_meta.restore_pending boolean` added.** BE-074 requires the store to refuse service until the newest deletion list is applied after a restore. A RAM-only flag would be lost on restart and would fail open. While the flag is set:
   - every source operation (`commit_envelope`, `apply_replies`, `lookup_account`, `create_account`, `update_account`, `delete_account`, `delete_replies`, `delete_mailbox`, `mailbox_list`) returns `RestorePending`; relay operations continue (AUD-RM2-STO-09);
   - `serving_allowed()` is false (RL-01 `restored`, C-06 busy page);
   - `PgIntakeStore::open` sets it on every initialised store at process start (failover to a recovered node, AUD-RM2-STO-05); `mark_restore_pending()` sets it for the runbook.
4. **Own migration runner and ledger `candor.schema_migration(version, sha256)`.** sqlx's `_sqlx_migrations` has `installed_on timestamptz`, which violates L11 (no time columns in the intake DB). Migrations:
   - are embedded with `include_str!` and are forward-only;
   - each run in a transaction with `lock_timeout = 10s` and `statement_timeout = 10min` (R7 SI-E-06);
   - are checked for drift by SHA-256. A changed applied migration is refused by both `migrate` and `open`.

   `intake_meta.schema_hash` = `SHA-256("candor/v1/intake/schema" ‖ Σ(u32be version ‖ SHA-256(sql)))` is written at `init` and checked at `open` (BE-050). `migrate()` is for `candorctl migrate` only. The service never migrates at start.
5. **RLS on every intake data table (stricter than 09).** 09 §5.1 says "no RLS needed (single tenant per DB)". R7 SI-E-03 and the coordinator ask for RLS, so it is added as defence in depth. `ENABLE` and `FORCE` are set on all data tables:
   - `intake_meta` is filtered by `tenant_id = current_setting('candor.tenant_id')`;
   - every other table is visible only while `intake_meta` is visible (an uncorrelated `EXISTS`).

   Every store transaction begins with `set_config('candor.tenant_id', …, true)` (SET LOCAL semantics). A store configured for the wrong tenant sees no rows and can write nothing. "Unique/FK keys include `tenant_id`" does not apply: intake tables carry no `tenant_id` (L11 forbids extra columns), and other tenants live in other databases, so cross-tenant unique probes are impossible. `schema_migration` holds no tenant data and has no RLS. The backup role must also SET LOCAL the tenant.
6. **Query functions, not `query!` macros** (assignment instruction: no live DB at compile time). R7 SI-E-05 prefers macros with a committed `.sqlx` offline cache. Compensating controls:
   - every SQL text is a `const &'static str`;
   - sqlx 0.9 accepts only `SqlSafeStr`;
   - `tests/source_lint.rs` fails if `src/` uses `AssertSqlSafe`, `QueryBuilder` or `format!` in `pg.rs`;
   - all values are bound.

   *Follow-up:* switch to `query!` once CI can produce the `.sqlx` cache.
7. **Deletion-list encodings** (04 §18.6 leaves them open):
   - `del_hash = SHA-256("candor/v1/intake/del" ‖ tenant_id(16) ‖ subject(32))`, where the subject is the `lookup_tag`, `mailbox_id` or REPLY `object_hash`;
   - `entry = u64be seq ‖ u8 kind(1 account, 2 mailbox, 3 reply) ‖ del_hash ‖ u32be del_day`;
   - `sig = Ed25519_K31("candor/v1/intake/deletion-list" ‖ prev_hash ‖ entry)`;
   - `prev_hash(1) = 0³²`;
   - `prev_hash(n+1) = SHA-256("candor/v1/intake/deletion-list" ‖ prev_hash(n) ‖ entry(n) ‖ sig(n))`.

   The relay must use `deletion::verify_chain` (or the same encoding). The label `candor/v1/intake/del` is not yet in candor-core's label registry (*feedback for candor-core owner*). The signer runs inside the DB transaction (`DeletionSigner`), because only that transaction knows the chain head.
8. **Dead-drop page format and lifecycle (AUD-RM2-STO-06/07).** Each entry is exactly 70,000 B: `u32be len ‖ reply_ct ‖ CSPRNG fill`, so `reply_ct ≤ 69,996 B` (09 says ≤ 70,000; the 4-byte prefix of 04 §13.5 must fit).
   - The set is a sequence of **generations**, one per fixed import slot (`generation = day × slots_per_day + index`). `rebuild_published_set(slot)` adds exactly K = `per_slot` entries: up to K pending real replies (oldest `available_day` first), topped up with fresh dummies; excess reals wait for the next slot. Missed slots are back-filled with dummy generations; the first publication back-fills the whole 30-day window. A repeated slot adds nothing.
   - Dummies are stored as `reply` rows (`source_account_id` NULL) exactly like Tier V replies, live exactly as long as real entries (same `available_day` = generation day, same expiry) and are never regenerated, also across restarts. `reply.pub_gen` records the generation (NULL = awaiting publication, 0 = padding pool).
   - The window therefore always holds K × 30 × `slots_per_day` entries; the page count is the next power of two of that (a constant of `DeadDropConfig`), and a persistent padding pool fills the last page. Two rebuilds differ by exactly K added and K expired entries whatever the real volume (tests `conf_dead_drop`).
   - Positions are uniformly random over **all** `page_count × 64` positions at every rebuild. `set_version` is a fresh random u64 per rebuild.
   - Pages are built once per rebuild and held in RAM as shared immutable buffers; every requester gets byte-identical pages and nothing about access is recorded.
   - Memory: `DeadDropConfig::validate` refuses more than `HARD_MAX_PAGES` = 128 pages (≈ 573 MB, the 08 SA-19 EE figure; peak ≈ 2 × during a rebuild). Pages are reserved with fallible allocation and filled by streaming 256 rows at a time; overflow is the typed `StoreError::Capacity`, never an OOM abort. The backlog of unpublished replies is bounded by `max_pending` (≤ 100,000); RL-05 rejects beyond it.
   - Implementation decision: the PostgreSQL store requires an explicit `DummyReplies` (no `RandomDummyReplies` default); production passes real-format sealed dummies.
   - **Dummy sizes (AUD-RM2-STO-19/25).** Every dummy's REPLY bucket is drawn independently with the CSPRNG from `DeadDropConfig::dummy_bucket_weights` (a public profile constant: one probability per canonical bucket k = 1..16, default `DEFAULT_DUMMY_BUCKET_WEIGHTS`, skewed to small buckets). `DeadDropConfig::validate` (run by both store constructors at startup, and again by every draw) fails closed unless each index is a canonical bucket (its `reply_ct_len` maps back to it and fits an entry), every weight is finite and ≥ `MIN_DUMMY_BUCKET_WEIGHT` = 0.005 (non-negative, and every canonical bucket covered, so no bucket is "real only"), and the weights sum to 1 within `DUMMY_WEIGHT_SUM_TOLERANCE` = 1e-6 (relative or tampered profiles such as "all weight on bucket 1" are refused); nothing is copied from a real reply, and the same draw sizes back-fill, padding and ephemeral dummies. `DummyReplies::dummy_body(bucket)` must return exactly `reply_ct_len(bucket)` bytes or the store refuses (fail closed). Deployments should set the weights to the long-run bucket distribution of their real replies (decision 26 residual).
9. **Window and expiry share one boundary.** A reply is published and retained iff `today − available_day < retention` (≤ 30). `expire_replies` clamps any retention above 30 down to 30.
10. **Tier W slots.** The store assigns the lowest free slot 0..31. If all 32 slots are taken, the reply is listed in `rejected` and the relay keeps it in `reply_outbox` for a later slot.
11. **Claim order and limits.**
    - Candidates are ordered by `(release_day, envelope_ref)`: the oldest released envelope goes first, so a high random ref cannot starve (AUD-RM2-STO-16); `release_day` is day-granular and never sent.
    - The first candidate is always taken, even if it alone exceeds `max_bytes`, so a large envelope cannot block the queue forever.
    - An ack listing a digest outside the batch changes nothing.
    - On ack, unacked envelopes of the batch return to the pool and the batch closes.
    - RL-02 `ref` is the intake-local `envelope_ref`. A re-offered envelope keeps its ref, which carries the same information as its unchanged `sha256`.
    - Bytes per group for `max_bytes` = three slot blocks + three padded blobs.
12. **Snapshot rollback rules (BE-060, RL-06).** Signature, witness and consistency verification belong to the KD verifier. The store enforces, atomically under a row lock:
    - `tree_size ≥ hwm`;
    - `checkpoint_day ≥ day_hwm`;
    - `version > directory_version`;
    - `consistent_from == hwm` (the proof must start from the stored mark).

    A re-push of the identical current snapshot returns `AlreadyInstalled`. Only the current and previous versions are kept. A DB trigger additionally refuses any decrease of `kd_tree_size_hwm`, `kd_checkpoint_day_hwm`, `directory_version`, `relay_req_counter` or `last_batch_no`.
13. **Quota (AUD-RM2-STO-01, ADR-052(14)).** Removed from the database: no `quota_bucket` column and no quota API. The daily upload quota lives in C-06/C-07 process RAM (a restart resets it, which is availability-only).
14. **Fixed sizes enforced:**
    - `disposition_ct` = 1,168 B (X-Wing Nenc 1,120 + 48; STD only, since FIPS is unsupported by candor-core);
    - `xwing_pk` = 1,216 B;
    - `prefs_ct` 1..4,096 B;
    - `size_bucket` 1..16 (REPLY buckets 4096·k).

    Part `padded_size` legality (ADR-011 bucket) is checked by the sealer/web, because the ciphertext overhead depends on the object format. The store only bounds it to 1..16 GiB.
15. **Deletions.**
    - Account deletion deletes the account and its replies (envelopes carry no account reference, ADR-052(2)).
    - `delete_mailbox` takes the reply refs from the caller, because the store has no mailbox column.
    - `deletion_list_after(after)` only reads; `after` above the head is `InvalidInput` (AUD-RM2-STO-10). Acknowledgement is `acknowledge_deletion_head(signed_head, core_pk)` (decision 27): the Z-CORE-signed head is stored as `intake_meta.deletion_acked_seq/_hash/_sig` (monotonic; the trigger requires the head to be in the local chain). Returned `relayed` = stored flag OR `seq ≤ acked`.
    - **Chain-extending inserts only (AUD-RM2-STO-21).** A `BEFORE INSERT` trigger (`deletion_list_append`) accepts an entry only if it extends the chain at the head (`seq = max + 1`, `prev_hash` = SQL chain hash of the head, computed with the built-in `sha256`) or below the oldest retained entry (`seq = min − 1`, its chain hash = that entry's `prev_hash`; restore and RL-12 merges insert in this order), or is the first entry of an empty list; `relayed` must be false and seq 1 must carry the zero genesis link. Restores and merges insert unflagged entries; "relayed" then comes from the acknowledged head.
    - **Append-only for the application role (AUD-RM2-STO-03).** `candor_istore` has `SELECT, INSERT` and a column `UPDATE (relayed)` that the trigger allows only as an unchanged rewrite (import-slot rewrite). Only the separate maintenance role `candor_intake_maint` may flip `relayed` (only for `seq ≤ deletion_acked_seq`) and `DELETE` (only relayed entries, never `seq = max(seq)`); the trigger checks `current_user`. The maintenance **process** (`PgIntakeMaintenance::open(…, core_pk)`) first re-verifies Z-CORE's signature on the stored acknowledged head and the local chain at that seq, and flags only up to that verified seq; a forged acknowledgement written by a compromised application role (the database cannot verify Ed25519) makes the prune fail with nothing flagged or deleted (AUD-RM2-STO-21). Retention rule (documented, enforced by `PgIntakeMaintenance::prune_deletion_list`): delete flagged entries with `del_day < today − 35`, never the head. The maintenance role runs in a separate process under its own OS user; `PgIntakeStore::with_maintenance` exists for tests and single-process setups.
    - No `SECURITY DEFINER` function is used (09 §10 allow-list): separation is by role, grants and trigger.
16. **Restore.**
    - `restore_backup` requires an empty store.
    - Counters and the KD high-water mark keep the higher of the backup and current values.
    - `apply_pushed_deletion_list(entries, signed_head, core_pk, k31_pk, hasher)` (AUD-RM2-STO-04/12/22): the Z-CORE head signature (decision 27), the entry signatures (strict Ed25519 under K31) and the internal chain are verified **before** the row lock; under the lock the run must end exactly at the signed head (seq **and** chain hash; a relay-claimed head is refused), be non-empty unless the local chain already contains the head, have head seq ≥ the last verified head, chain to the last verified head (the entry at its seq hashes to it, or its successor links to it), start no later than local head + 1 (no gap), link to the local entry before it or overlap the local list (unanchored only when the local list is empty), match every overlapping entry (no fork), link each filled hole to its local successor, and leave a contiguous merged list. Lookups are `BTreeMap`/`HashSet` (no quadratic work). Any validation failure **persists** restore-pending, also on a serving store. Then newer entries are merged and every listed account (by `del_hash` of `locator_hash`) and listed reply (by `object_hash` via `ReplyObjectHasher`; the default `CoreReplyHasher` uses candor-core's `object_hash` over the first 160 bytes of `reply_ct`) is deleted.
    - `MAX_PUSHED_DELETION_LIST` lowered to 200,000.
    - `restore_backup` refuses a backup whose `kdf_salt` differs from an initialised target (`Conflict`, AUD-RM2-STO-15) and validates the whole backup before writing.
    - The deletion list inside a backup is not re-verified at restore (the backup is authenticated by the backup system, 19), but it must be one linked run and its `MetaSnapshot.deletion_head` (the last verified Z-CORE head, AUD-RM2-STO-22) must lie in it. The restored store keeps that head, so a later push must chain to it. On success the pushed head becomes the verified head.
17. **Durability.** `commit_envelope` returns after `COMMIT`. With `fsync = on` and `synchronous_commit = on` (the default), that means after the WAL flush (ADR-046(1), BE-071). *Spec feedback:* add `synchronous_commit = on` to the 09 §10 intake hardening table. Blob files must be fsynced by the caller **before** `commit_envelope`. `ack_batch` returns the blob ids the caller must delete (BE-014).
18. **Roles in the migration.** Roles are created idempotently in a `DO` block, which needs CREATEROLE: test clusters run it as superuser; production provisions the roles at deployment with the same attributes (ADR-052(9): `candorctl migrate` runs as OS user `candor-migrate`, peer-mapped to the migration role). The migrator receives `CREATE ON DATABASE` and owns every object. `candor_istore`, `candor_intake_maint` and `candor_intake_backup` own nothing and have `NOSUPERUSER NOBYPASSRLS NOCREATEROLE NOCREATEDB NOREPLICATION`. They get per-database `search_path = candor`. The app and maintenance roles get `statement_timeout 30s` and `idle_in_transaction_session_timeout 60s`, and `temp_file_limit 1GB` (superuser-only setting: applied by the migration when run as superuser, else by provisioning); the backup role gets `default_transaction_read_only`. The app role's `intake_meta` UPDATE is column-level (no `tenant_id`, `schema_hash`, `kdf_salt`, `config_version`); the trigger also makes tenant, salt and schema hash immutable (AUD-RM2-STO-08).
    - `open` (both roles) re-asserts `statement_timeout`, `idle_in_transaction_session_timeout`, `lock_timeout`, `search_path`, `synchronous_commit`, `row_security` and `default_transaction_read_only` as startup options (they take precedence over role and database defaults), and refuses: superuser, BYPASSRLS, membership in any role owning a `candor` table, in the database owner (allowed only for the maintenance role, which is the owner), or in the other intake role; any data table without `ENABLE`+`FORCE` RLS; a policy set other than exactly one permissive `p_tenant` (all commands, PUBLIC) per data table; and a disabled guard trigger (AUD-RM2-STO-08).
   - **Role defaults (AUD-RM2-STO-08, round 4).** PostgreSQL lets every ordinary role `ALTER ROLE` its own session defaults (cluster-wide or per database); this cannot be revoked in PG 16 (verified: the app role can, `pg_role_defaults_and_live_guards`). The store therefore checks, at `open` and in `after_connect` for **every** new pool connection, that every stored default of the role (`pg_db_role_setting`, cluster-wide and this database) is one of the migration's values (`idle_in_transaction_session_timeout=60s`, `search_path=candor`, `statement_timeout=30s`) or a `temp_file_limit` (superuser-only, so not role-written), and that the effective session values are the expected ones (`session_replication_role = origin`, `default_transaction_isolation = read committed`, …) with an effective `temp_file_limit` between 1 kB and 1 GB (never unlimited; the deploy's server-wide 256 MB passes); any deviation refuses the connection (fail closed). The role can neither set nor reset `temp_file_limit` (tested).
   - **VACUUM by the maintenance role, not the schema owner (AUD-RM2-STO-24(a)).** `candor_intake_maint` (OS user `candor-imaint`, deploy D-34) **owns the database** but no table and no schema, and is no member of the schema owner. PostgreSQL 16 lets the **database owner** VACUUM (also FULL) every non-shared table in the database without table ownership (`vacuum_is_permitted_for_relation`; verified live: `pg_vacuum_login_identity`, `pg_vacuum_full_erases_old_images` vacuum and rewrite every intake relation as this role). So no `SET ROLE` to the owner is needed. *Coordinator/deploy proposal (NOINHERIT membership of the maintenance login in the schema-owner role, `SET ROLE` only around VACUUM) not adopted:* a member that can `SET ROLE` to the owner holds the owner's full capability in a routinely running process (disable RLS/triggers, alter grants, drop tables) — exactly AUD-RM2-STO-24(a) — and NOINHERIT does not restrict `SET ROLE`; database ownership gives VACUUM without any of that. The maintenance role cannot `ALTER TABLE` (no `DISABLE TRIGGER`, no `NO FORCE ROW LEVEL SECURITY`), cannot read source rows and cannot `SET ROLE` to the migrator; the app role cannot VACUUM (PostgreSQL skips the table, file unchanged) and cannot `SET ROLE` to the owner or the maintenance role (all tested). It holds `pg_checkpoint`. `vacuum_after_rewrite`/`vacuum_full_daily` refuse to run unless the connected role owns the database and is not superuser, BYPASSRLS, the schema/table owner (or a member) or a member of `candor_istore`/`candor_intake_backup`; the app's `open` refuses membership in the database owner. The migration login (`candor-migrate`) is used only by `candorctl migrate`. Residual: a database owner can `DROP DATABASE`, `ALTER DATABASE … SET` (unsafe settings are caught by the per-connection session check) and `CREATE` schemas (the service roles use `search_path = candor` and schema-qualified SQL). PG ≥ 17: `GRANT MAINTAIN` / `pg_maintain` instead of ownership.
19. **L11 wording conflicts with 09 §5.1.** L11 bans `kind` and `last_*` columns, but §5.1 itself defines `deletion_list.kind` and `intake_meta.last_batch_no`. The lint exempts exactly those two (*spec feedback*).
20. **Concurrent migrations.** Cluster-wide role DDL races ("tuple concurrently updated"), so tests serialise `migrate`. Production runs one `candorctl migrate` at a time.
21. **Fixed-shape envelope groups (ADR-052(1)).** An envelope row is one group of exactly three objects in order (main SUBMISSION/SOURCE_MESSAGE, ATTACHMENT_BUNDLE, IDENTITY). Each `envelope_part` row (part_no 0..2) holds the object's `object_hash`, its RecipientSlotBlock (exactly 18,692 B, STD) and its blob reference. 09's `header_ct`/`manifest_ct` columns are replaced (the sealer emits sealed objects with slot blocks, `candor-sealer` `EnvelopeObject`). The relay ack digest is `group_sha256 = SHA-256("candor/v1/intake/group" ‖ object_hash₀ ‖ object_hash₁ ‖ object_hash₂)` (`types::group_digest`); RL-02 carries the three object hashes and padded sizes; RL-03 selects `SlotBlock(i)` or `Object(i)`. Blob ids and object hashes within a group must be distinct.
22. **Accounts separate from envelopes (ADR-052(2)).** Envelope rows carry no account reference. `create_account` (also used by chaff for dummy accounts), `update_account` (passphrase rotation: tag, keys, prefs) and `purge_inactive_accounts` (09 `inactive_purge`: `activity_month` started ≥ 365 days ago; abandoned real and dummy accounts expire alike) are separate operations. This supersedes ADR-034's "account in the same transaction as the first envelope".
23. **Import-slot rewrite and activity (AUD-RM2-STO-01).** Account rows change only on create, update (rotation), delete and `uniform_rewrite(slot, counters, active_accounts)`. The web records active accounts (envelope commit) in RAM, like quota, and flushes them at the slot: `activity_month` becomes the slot's month for those accounts and the month of any stored reply ≤ the slot day for Tier W reply arrivals. In the same transaction the RAM-accumulated `counter_month` deltas are added (all-or-nothing, overflow checked in SQL without raising) and every row of `source_account`, `envelope`, `envelope_part`, `reply`, `deletion_list`, `counter_month`, `directory_snapshot` and `intake_meta` is rewritten, so all share one `xmin` (test `pg_uniform_rewrite_xmin`). `counter_add` was removed: counters can no longer be written next to a real envelope. Call order at each slot: relay work (claim/ack, RL-05, RL-11), `rebuild_published_set`, then `uniform_rewrite` last.
24. **Day coarsening (AUD-RM2-STO-01).** `directory_snapshot.applied_day` is stored as the first day of the month (spec gives no granularity; CHECK enforced). `reply.available_day` is the import-slot day: RL-05 runs only in slots, and publication resets it to the generation's slot day; it stays a day because the 30-day retention and window are day-based (09 "Day granularity"). `deletion_list.del_day` stays the deletion day: it is signed into the chain and Z-CORE computes its own 35-day retention from it (09 §5.2.7), so a month would shorten Z-CORE retention (a weakening); see spec feedback. `envelope.received_date` stays a day (09). After the slot rewrite these days anchor only the slot's `xmin`.
25. **Migration 0001 amended in place.** No intake database has been deployed from this crate (the step has not passed its audit gate), so the fixes amend `0001_intake_schema.sql` rather than adding 0002; the ledger hash changes accordingly.
26. **Canonical REPLY lengths (AUD-RM2-STO-20).** `reply_ct` must be exactly `reply_ct_len(k) = 4096·k + 1418` (STD: CoreHeader 128 + header_mac 32 + one STREAM tag 16 + HPKE_BASE stanza 1242; checked against candor-core in `types::tests::reply_ct_len_matches_core`). The stored `size_bucket` of every row (real or dummy) is `reply_bucket_of_len(len)`; RL-05 rejects a reply whose length is not canonical or whose reported bucket differs. Residual: the published entries' cleartext length prefixes still reveal each entry's bucket, so a real reply in a bucket the dummy profile rarely draws stands out statistically; *spec feedback*: pad every REPLY ciphertext to one length, or move `entry_len` inside the encryption.
27. **Z-CORE head attestation (AUD-RM2-STO-21/22/24).** `SignedDeletionHead { seq, head_hash = chain hash through seq, day, counter, sig = Ed25519_core("candor/v1/intake/deletion-head" ‖ tenant ‖ u64be counter ‖ u32be day ‖ u64be seq ‖ head_hash) }`; `core_pk` is intake configuration. `day` is Z-CORE's day of the attestation; `counter` is Z-CORE's per-tenant attestation counter, strictly increasing with every head it signs (≥ 1). Neither acknowledgement nor RL-12 trusts a relay-asserted number. Rules (`SignedDeletionHead::newer_than`, `check_fresh`):
    - **Monotonic** against the last verified head (stored as `intake_meta.deletion_acked_seq/_hash/_sig/_day/_counter`, carried in backups as `MetaSnapshot.deletion_head`): a lower counter is refused ("older than the verified head"); the same counter must be the identical attestation; a newer counter must not lower `day` or `seq`. Applies to RL-11 (`acknowledge_deletion_head`, which now *refuses* an older head instead of ignoring it) and RL-12/restore. A newer attestation of the same seq refreshes the stored head (raises the floor). The DB trigger refuses any change of the stored head without a higher counter, and any decrease of counter or day.
    - **Fresh** for RL-12 and restore: `apply_pushed_deletion_list(…, today)` requires `today − 1 ≤ head.day ≤ today + 1` (`MAX_HEAD_AGE_DAYS`; `today` from the caller, the store reads no clock). This closes the old-backup replay: a node restored from a backup older than a genuine head H_o (whose counter is above the backup's) refuses H_o once it is more than a day old; Z-CORE re-attests its current head at every relay cycle. Test `conf_head_replay_after_restore` (both stores).
    - Residual: within the one-day freshness window, a relay holding two genuine attestations of that window can still push the older one to a node restored from a backup older than both (deletions in between are applied at the next push, which must be newer). *Spec feedback*: define day/counter in 08 RL-11/RL-12 and the key in 04/05; optionally bind the attestation to an intake challenge.
28. **TOAST and post-rewrite VACUUM (AUD-RM2-STO-18).** `uniform_rewrite` re-creates every out-of-line value (`envelope_part.slot_block`, `reply.reply_ct`, `directory_snapshot.body/signatures`) with `col || ''` (a computed datum: PostgreSQL stores a new TOAST value; an unchanged column keeps the old TOAST tuples, proven by a mutation run of `pg_uniform_rewrite_toast`), one row per statement in a CSPRNG-shuffled order across the three tables, so new `chunk_id`s follow the shuffle. `source_account` and `envelope` use `toast_tuple_target = 8160`, so their rows (≤ ~5.5 KB) never go out of line; ciphertext columns are `STORAGE EXTERNAL` (no pointless compression). `vacuum_after_rewrite(maint_opts)` runs a plain `VACUUM` of the eight tables as the maintenance role (database owner, decision 18; no longer the migration login, AUD-RM2-STO-24(a)), never from the service roles; autovacuum is off (decision 29) and `vacuum_full_daily` erases what plain VACUUM leaves in page free space (decision 30). Per-row statements give each row its own `cmin`, which follows the shuffle (no creation order). Cost: each slot rewrites every slot block, reply and snapshot (≈ window × 70 KB + pending envelopes × 56 KB of heap/WAL per slot).
29. **No cumulative statistics, no autovacuum (AUD-RM2-STO-11).** The intake cluster runs with `track_counts = off` and `autovacuum = off` (deploy-owned, table below; the test cluster's default profile does the same, and the whole suite also passes with PostgreSQL's defaults, `CANDOR_TEST_PG_PROFILE=stock`). The store does not depend on either: it reads no statistics, and VACUUM is scheduled — plain VACUUM at every fixed import slot (`vacuum_after_rewrite`) and VACUUM FULL daily (`vacuum_full_daily`) — so its timing follows the slot schedule, never source activity. Every intake table and its TOAST table also has `autovacuum_enabled = false` (migration), which holds even if the cluster setting is forgotten. PostgreSQL still forces an anti-wraparound VACUUM near `autovacuum_freeze_max_age` whatever these settings (a fixed xid count, not a time). The store never runs `ANALYZE`: `pg_statistic` would copy sampled column values (locator hashes, days) outside the rows, where they outlive deletions; planner statistics are not needed at intake sizes. `pg_stat_reset()` stays in the daily job as defence in depth.
30. **Daily VACUUM FULL in a fixed maintenance window (AUD-RM2-STO-23).** Plain VACUUM leaves pre-rewrite tuple images (old `xmin`, old TOAST `chunk_id`) in page free space (the audit's raw-page PoC). `vacuum_full_daily` rewrites all eight source-linkable tables with their TOAST tables and indexes into new relation files (old files are truncated at commit and unlinked by the following `CHECKPOINT`), as the maintenance role (database owner). Measured with the audit's probe (`pg_vacuum_full_erases_old_images`): after the slot rewrite + plain VACUUM, `[old xmin][rewrite xid]` headers and old chunk ids are found in the raw pages (positive control); after `vacuum_full_daily`, none in any page of any intake table, TOAST table or index, every relfilenode is new, and the store content and the single slot `xmin` are unchanged (VACUUM FULL keeps live tuple headers; live chunk ids were already re-created in shuffled order). **Lock/availability:** VACUUM FULL takes an ACCESS EXCLUSIVE lock on each table in turn (one transaction per table) for a time proportional to its size (≈ 0.5–1 GB in the largest EE profile: the 30-day reply window and pending envelope parts) and needs that much free disk temporarily. Intake serving (source web, relay control) **pauses for the window** (C-06 busy page; the relay retries); the window is a fixed daily time after the last import slot (e.g. 03:30 UTC for 4 slots/day), never triggered by activity. Session limits of the VACUUM connection: `statement_timeout = 30min`, `lock_timeout = 60s`; on error the job retries within the window and alerts (remaining tables keep their images until the next successful run). Residual: between a slot and the next daily run (≤ 24 h) old images remain in free space (the plain-VACUUM state the audit measured); WAL keeps them until recycled (09 §13).
31. **Staged-bundle hand-over by descriptor (deploy D-33, ADR-055(1), AUD-RM2-STO-27; `staged` module).** The store has no access to the sealer's staging. `StagedReceiver::new(blobs, sealer_uid, max_len)` (no default uid) owns the blob root. `receive(sock, slot)` checks, in this order: `SO_PEERCRED` uid = `sealer_uid` (else refused *before* reading, no answer); socket is `SOCK_SEQPACKET`; one `recvmsg` under `SO_RCVTIMEO` (default 5 s, clamped 10 ms..60 s; expiry → `InvalidInput("staged receive deadline")`); no `MSG_TRUNC`/`MSG_CTRUNC`; exactly one control message, `SCM_RIGHTS` only (credentials or a second control message refused), exactly one descriptor (all received descriptors owned and closed, `MSG_CMSG_CLOEXEC`); exactly 41 bytes, version 2 (protocol 2, decision 33), `1 ≤ len ≤ min(max_len, STAGED_MAX_BUNDLE_LEN = 4 GiB)`; `fstat` regular file; `F_GET_SEALS` ⊇ `WRITE|GROW|SHRINK|SEAL|EXEC` (`EXEC` added in round 6: the sealer creates memfds with `MFD_NOEXEC_SEAL`; Linux ≥ 6.3. Test fixtures use `MFD_NOEXEC_SEAL` too, because adding `F_SEAL_EXEC` to an executable memfd makes the kernel imply WRITE/GROW/SHRINK and would mask the missing-seal variants) (fails on any file that is not a sealable memfd, so FUSE/NFS/disk files are refused); `st_size = len`. The copy (`pread` from offset 0, never written) goes into a `candor-safefs` object under a pre-registered random id; EOF probe and constant-time SHA-256 check before the safefs commit (fsync, no-replace rename, slot times). Once the safefs commit returns, `receive` sends the copied acknowledgement `0x02 ‖ sha256` before returning the blob (decision 33). Any refusal after the message was dequeued answers `0x00 ‖ 0³²` (best effort, under `SO_SNDTIMEO`). `commit_staged(store, envelope, blob)` requires the ATTACHMENT_BUNDLE object (index 1) and no other to name the blob with `padded_size = len`, then calls `commit_envelope` (returns after `COMMIT`) and returns a `CommittedStaged` token (private fields, not `Clone`); `acknowledge(sock, token)` is the only way to send the commit acknowledgement `0x01 ‖ sha256`. Blocking calls except `commit_staged`. `send_staged_bundle` is the matching send side (tests; the sealer has its own in `server::handover`, same wire format).
32. **STO-27 implementation decisions.**
    - *Deadline without a clock.* The crate never reads a clock (`tests/source_lint.rs` bans `Instant::now`). The total time of a receive is bounded structurally: one `recvmsg` under `SO_RCVTIMEO`, then a copy of at most `max_len` bytes from a sealed shmem file (RAM; cannot block on a remote or FUSE filesystem because only sealable memfds pass), then at most one `send` under `SO_SNDTIMEO`. The acknowledgement send has the same deadline. A daemon should call `receive` when the socket is readable; on any error it closes the connection (the sealer fails closed and reconnects).
    - *Commit outcomes.* `Ok` → token. A rejection before the transaction (`InvalidInput`, `DuplicateEnvelope`, `RestorePending`, `NotInitialized`, …) → orphan. `Backend` is ambiguous (the error may follow `COMMIT`): retried once with the same envelope; `Ok` → token; any error on the retry → no token, no `0x01`, the blob is counted (`uncertain_count`) and protected from the sweep for one full slot (a late `COMMIT` lands well within the 30 s statement timeout), after which the database reference check decides. A commit future dropped mid-await is treated the same (guard).
    - *Orphan sweep (lead-approved 2026-10-01).* `sweep(refs, slot)` runs at start-up (`startup`, after `purge_incomplete`) and at every slot boundary with that slot. It lists the staged blob directory, then snapshots the in-memory registry (a listed blob was registered before its file existed, so an in-flight one is always seen), and removes a blob only if it is **not in flight** (receiving, held as `StagedBlob`, committing, or uncertain for less than one sweep) **and** `IntakeMaintenance::blob_referenced` returns `false`. Any lookup error aborts the sweep with nothing unchecked removed (fail closed). Known orphans first, then unregistered blobs (crash leftovers), each group in CSPRNG-shuffled order; at most `STAGED_SWEEP_MAX_CHECKS` (1024) lookups and `STAGED_SWEEP_MAX_REMOVALS` (64) removals per slot, removals themselves shuffled; safefs `remove` sets directory times to `slot`. No journal, marker file or log entry is written. **Deploy rule:** the staged blob directory is used by `StagedReceiver` only (any other unreferenced object in it would be removed).
    - *`blob_referenced` (new `IntakeMaintenance` method).* `SELECT EXISTS (SELECT 1 FROM candor.envelope_part WHERE blob_id = $1)` (unique index), bind parameter, statement logging disabled, read-only transaction rolled back. **Fails closed (AUD-RM2-STO-28):** the lookup runs in the same transaction as the tenant-scoped `intake_meta` read (`begin(false)`); if row-level security hides the tenant row (wrong tenant, uninitialised or restored-empty database) it returns `NotInitialized`, and a visible row naming another tenant returns `TenantMismatch`, so "no rows visible" is never read as "unreferenced". The sweep aborts on any error (`pg_staged_crash_between_copy_and_commit` covers wrong tenant and empty database). Least privilege: `PgIntakeStore` runs it as the application role `candor_istore`, which already has `SELECT` on `envelope_part` — **no grant or schema change** (schema hash unchanged). The maintenance role has no access to that table and is not given any; `PgIntakeMaintenance::blob_referenced` fails closed (`Integrity`). `MemoryStore` checks its envelopes and, like PostgreSQL, returns `NotInitialized` when uninitialised (round 6; `staged_sweep_uninitialised_memory_store_fails_closed`).
    - *Bounded state.* At most `STAGED_MAX_IN_FLIGHT` (64) registered blobs per receiver (received, committing or orphaned); beyond that a hand-over is refused (`Capacity`, `0x00`) before anything is written.
    - *Seam.* `commit_staged` takes any `StagedCommit` (blanket-implemented for every `IntakeStore`). This is no weaker than taking `IntakeStore` (a public trait anyone can implement) and lets tests inject backend errors and cancellation.
    - *Residual.* A blob of a committed envelope that the relay later acknowledged (`ack_batch` → `blobs_to_delete`) and that the caller has not yet deleted is also unreferenced, so the sweep removes it too — intended. Sweep filesystem calls block briefly inside an async fn (one listing, ≤ 64 unlinks per slot).
    - *Commit deadline (lead decision, round 5; the sealer keeps its 60 s ack timeout).* Each `commit_envelope` attempt of `PgIntakeStore` is capped inside its transaction: the first statement after `BEGIN` sets the tenant and `SET LOCAL statement_timeout = lock_timeout = 2500 ms` (`SQL_COMMIT_SCOPE`, transaction-local, reverts at the end). Six statements run under it (read `intake_meta`, insert envelope, 3 × insert part, `COMMIT`) → ≤ 15 s, plus the application pool's acquire bound of 5 s (`APP_ACQUIRE_TIMEOUT`; it includes connection set-up and the session check) → **≤ 20 s per attempt**. The lead asked for a 20 s statement and lock timeout per attempt; `statement_timeout` is per *statement* and PostgreSQL 16 has no `transaction_timeout`, so 20 s per statement would allow 6 × 20 s; the per-statement value is therefore 20 s divided over the attempt (implementation decision, keeps the 20 s attempt bound real). A statement/lock timeout (`57014`, `55P03`) or an expired pool acquire maps to the new `StoreError::Timeout`: it happens before `COMMIT` completes (a commit in progress is not interruptible), so nothing was committed — `commit_staged` treats it as a definite refusal (no retry; the blob is an orphan for the sweep; the caller sends `0x00`). Only `Backend` is retried, once → ≤ 40 s for both attempts. Budget to the sealer's 60 s: copy into safefs (RAM read + one fsync, bounded by `max_len`; deploy must size `max_len` so this stays ≤ 4 s on the intake volume) + ≤ 40 s commits + the 33-byte ack (immediate; ≤ `SO_SNDTIMEO`) → **≤ 45 s worst case**. *Protocol 2 (decision 33):* the copy is now acknowledged separately with `0x02` under the sealer's length-scaled copy deadline, and the sealer's 60 s starts at `0x02`, so only the ≤ 40 s of commits plus the ack fall under it. Residual: `BEGIN` and the scope statement itself run under the role default (30 s) before the cap applies; they take no locks. Test: `pg_staged_stalled_commit_refused` (another session holds `ACCESS EXCLUSIVE` on `envelope`; refused with `Timeout` in ≥ 2 s and < 20 s, nothing committed, orphan swept).
    - *Wire `0x01` meaning.* Unchanged from the sealer: the envelope referencing the copy is committed. The sealer's `await_ack` treats any other answer, EOF or timeout as failure.

33. **Hand-over protocol 2 (AUD-RM2-STO-29, C-5; lead dispositions after round 6).** Both ends (`staged` here, `candor_sealer::server::handover`) speak version 2:
    - *Message.* Unchanged shape: `u8 version = 2 ‖ u64be len ‖ sha256` (41 bytes) plus one sealed memfd (`SCM_RIGHTS`). A version-1 message is refused.
    - *Acknowledgements.* Always 33 bytes, `u8 code ‖ 32 bytes` (`STAGED_ACK_LEN`):

      | Code | Sent by | When | Hash field |
      |---|---|---|---|
      | `0x02` (`STAGED_ACK_COPIED`) | `receive` | after the safefs commit of the copy (durable), before returning the blob | the bundle's SHA-256 |
      | `0x01` (`STAGED_ACK_COMMITTED`) | `acknowledge(token)` | after `commit_staged` returned a `CommittedStaged` | the bundle's SHA-256 |
      | `0x00` (`STAGED_ACK_REFUSED`) | `refuse` / any refusal after the message was dequeued | nothing committed | 32 zero bytes |

      A successful hand-over therefore carries exactly `0x02 ‖ h`, then `0x01 ‖ h`. A refused commit carries `0x02 ‖ h`, then `0x00 ‖ 0³²`; a refusal before the copy is durable carries only `0x00 ‖ 0³²`.
    - *Sealer side.* It waits for `0x02` within `10 s + ⌈len / 50 MB/s⌉` and then for `0x01` within 60 s, checks the hash echo, and fails closed on anything else (including the old one-byte ack). The deploy requirement that the blob volume sustains ≥ 50 MB/s is not yet checked by anything (deploy-owner open item).
    - *One cap.* `STAGED_MAX_BUNDLE_LEN` (4 GiB) = the sealer's `MAX_BUNDLE_LEN`; `StagedReceiver::new` clamps `max_len` to it.

## Security self-review

Checked as an attacker (ASVS 5.0 L3 mindset, BUILD-BRIEF "Security and OPSEC bar"):

- **Metadata.**
  - No column, value or code path holds an IP, User-Agent, circuit data, filename or time finer than a day. Live and static lints prove this for types and names, and `pg_no_exact_times_stored` checks the values.
  - The store reads no clock; `source_lint` forbids it.
  - Commit timestamps are unavailable (`track_commit_timestamp = off`, tested).
  - IDs are 128-bit CSPRNG values.
  - Claim order is `(release_day, random ref)`; `release_day` never leaves the intake.
  - Source actions never write account rows; the import-slot rewrite gives every source-linkable row one `xmin` (live test); quota is RAM-only; counters are written only at the slot.
  - Envelopes carry no account reference (ADR-052(2)).
  - No expected outcome raises a server error, so nothing about a source action reaches the PostgreSQL log (live test with captured log and a positive control).
  - Dead-drop diffs reveal only K added / K expired per slot.
  - `set_version` is random.
  - No per-mailbox access state exists.
  - Debug output of every source-linked type is redacted.
  - Errors carry only static strings. PostgreSQL error details, which can echo `locator_hash` values, are discarded.
- **Logging.**
  - sqlx statement logging is disabled on every connection (tested by source lint).
  - The test cluster uses `log_min_messages=panic`, `log_parameter_max_length*=0`, `log_min_error_statement=panic` and `log_statement=none`; the log goes to a 0600 file only so a test can read it.
  - No `print`, `log` or `tracing` in `src/`.
- **SQL injection.** All SQL is static; no dynamic SQL is possible without `AssertSqlSafe`, which is banned.
- **Least privilege.**
  - The app and maintenance roles are non-owner, NOBYPASSRLS, non-superuser, not members of an owning role or of each other; RLS forced and guard triggers enabled; all verified at `open`.
  - The app role has no TRUNCATE or DDL, no DELETE on `deletion_list`, and column-level UPDATE on `intake_meta` without the identity columns.
  - Only the maintenance role flags and prunes deletion-list entries (acknowledged only, never the head; tested including the two-statement bypass).
  - The backup role is read-only on exactly three tables.
  - DB triggers enforce monotonic counters, immutable identity and the acknowledged-seq bound.
  - Session settings are re-asserted per connection as startup options, and the role's stored defaults and effective values are checked on every new connection (a role can rewrite its own defaults).
  - VACUUM runs as the maintenance role, which owns the database but no table or schema (cannot disable guards, read source rows or become the schema owner); the migration login is never used by a scheduled job.
- **Network.** Unix socket only: no TLS feature is compiled and there is no TCP in tests (`listen_addresses = ''`, peer auth with an ident map, no host lines).
- **Fail closed.**
  - Restore-pending persists across restarts and is entered at every PostgreSQL process start.
  - Forged, forked, gapped, truncated, unanchored or empty-when-expected deletion lists are rejected, and the rejection persists restore-pending.
  - Every source operation refuses while restore-pending.
  - Schema drift refuses `open`.
  - CSPRNG failure is an error.
  - Unknown enum text from the DB is an `Integrity` error.
  - Oversized inputs are rejected before any DB work.
- **Input handling.**
  - Every external input has an explicit maximum: group shape (exactly 3 objects, fixed slot-block length), part size, reply size, reply count per push, publication backlog, published pages (typed `Capacity`, fallible allocation, streamed build), snapshot body and signatures, pushed list length, deletion page size, claim limits, active accounts per slot.
  - Day values are bounded before date arithmetic.
  - There is no recursion.
  - No `unwrap`, `expect` or indexing on untrusted data (clippy deny set clean).
  - Duplicate refs and blob ids are rejected.
- **Secrets.** The only secret in reach is K31, inside candor-core's zeroizing `SigningKey` (redacted Debug), used through `DeletionSigner`. The KDF salt is public.
- **Residual risks.**
  1. The mailbox-entry restore gap.
  2. `RandomDummyReplies` (tests, `MemoryStore::new`) lacks CoreHeader magic; the PostgreSQL store requires an explicit `DummyReplies`, and production must pass real-format sealed dummies (C-08 daemon), else an observer can tell dummies from real replies by structure.
  3. TOAST and storage (AUD-RM2-STO-18/23, decisions 28, 30): after the rewrite and VACUUM every live heap and TOAST tuple carries the slot's `xmin` and the chunk_ids follow a random order (tested on raw pages). Pre-rewrite tuple images stay in page free space until the daily VACUUM FULL (≤ 24 h), which erases them from every intake relation (tested with the raw-page probe); the old files' blocks are freed by the filesystem (ciphertext under LUKS, like WAL). Remaining: WAL segments until recycled; the OID counter's position (a count, not a time); the VACUUM FULL output order follows the existing physical order.
  3a. Between two slot rewrites, rows written since the last slot (new accounts, envelopes, deletion entries) carry their own `xid`, so a live-DB observer sees their order within that interval (≤ one slot spacing), e.g. an account creation adjacent to an envelope commit (diluted by chaff accounts, ADR-052(2)). The rewrite also keeps rows roughly in their physical (`ctid`) order (VACUUM FULL compacts but keeps that order). Dead tuples and WAL keep old versions until vacuum/recycle (09 §13). Tables with BEFORE UPDATE triggers keep a lock-only `xmax` equal to the rewrite's own `xid` (no extra information; asserted).
  4. A compromised application role can still clear `restore_pending` (the database cannot verify K31 signatures without an extension or a definer function, both excluded by 09 §10); the grants and trigger only stop identity and monotonic-value tampering.
  5. A real reply deleted by its source (or by account deletion) disappears from the published set at the next rebuild while dummies never leave early, so an observer learns that an entry was real and was deleted at that slot (AUD-RM2-STO-14; 08 SA-19 requires removal). The removal is shown only at slot granularity (BE-063).
  6. After a restart, or if a concurrent purge removed rows during a rebuild, missing positions are filled with ephemeral dummies (regenerated at the next rebuild); their number depends only on deletions, not on reply volume.
  7. Cumulative statistics (AUD-RM2-STO-11): with `track_counts = off` no per-table counters or vacuum timestamps exist; `pg_class.relpages/reltuples` are updated by the slot VACUUM (slot-granular sizes, an aggregate); the deploy must remove `pg_stat/` around restarts (table above). Not enforced by the store (deploy-owned).
  7a. The maintenance role owns the database: it can `DROP DATABASE` or `ALTER DATABASE … SET` (availability; unsafe settings are caught by the per-connection session check). PG ≥ 17 `MAINTAIN` would remove this.
  7b. Intake serving pauses during the daily VACUUM FULL window (fixed time; availability only).
  8. Lookup timing for unknown and known `lookup_tag` is the caller's job (BE-010 floor).
  9. Query macros with an offline cache are deferred (decision 6).
  10. Dummy bucket profile vs real distribution (decisions 8, 26; AUD-RM2-STO-25): the weights are validated at startup (canonical buckets, floor, sum 1), but if real replies' buckets deviate from the configured profile, per-slot length multisets still leak statistically (a rare-bucket real reply has likelihood ratio ≈ real share / weight); calibration is a deployment duty; a database seizure cannot separate rows (tested).
  11. Replay of an older genuine Z-CORE head within the one-day freshness window to a node restored from an older backup (decision 27).
  12. The maintenance *role*'s raw SQL access can still flag up to the stored acknowledged seq without the signature check (only the maintenance process verifies); exploiting this needs the maintenance credentials plus a forged acknowledgement by the application role.
  13. The PostgreSQL tests return early without a message when `CANDOR_TEST_PG` is unset: the workspace clippy configuration bans stdio and filesystem path APIs (LOG-001, ADR-027), so the skip message and direct file reads were removed (the server log is read through `pg_read_binary_file`, sources through `include_str!`).

14. **Staged hand-over (STO-27 self-review).** Checked: no `unwrap`/indexing on peer data (`get`, checked arithmetic, strict decode); every received descriptor is owned and closed on every path (tested with `/proc/self/fd`); the peer check precedes reading; no unbounded wait (socket deadlines, sealed RAM-backed file only); no unbounded memory (64 KiB zeroized buffer, 64 in-flight blobs); errors are static strings without sizes, ids or paths; `Debug` of `StagedBlob`/`CommittedStaged`/`StagedReceiver`/`StagedHeader` is content-free; no logging; no on-disk record of failures; `0x01` requires a token created only after `commit_envelope` returned `Ok` for an envelope naming exactly this blob. `safefs-lint` markers only on the `rustix::fs` import of `fstat`/`fcntl_get_seals` (fd-only). Residuals: (a) sweep correctness relies on the staged directory being exclusive to the receiver (deploy rule, decision 32) and on `blob_referenced` failing closed; (b) the peer check is by uid only — any process of the sealer's uid can hand over, which is the sealer's own trust boundary; (c) `SO_PEERCRED` reflects the credentials at `connect()` time (a descriptor passed on to another process keeps them), so `istore.sock` must stay 0660 to the sealer group with the sealer the only member (deploy); (d) control messages that the receiving socket opts into (`SO_PASSCRED`, `SO_PASSSEC`) are refused only if rustix decodes them (`SCM_CREDENTIALS`); others are silently skipped by rustix — the daemon must not enable those options.
